# Generated frontend rejection campaigns

`negative-source-v1` generates bounded Script and Module entry sources with
missing initializers, unterminated strings, duplicate lexical or private names,
duplicate prototype setters, surviving cover initialized names, unowned Super
references and strict Delete. A closed source owner fixes the offending
construct, parse goal, strictness and expected product phase. One to thirty-two
statements and depth one to four bound all source generation. Reduction removes
irrelevant statements, block nesting and literal/name payloads while retaining
the same rejection owner and original budget.

The actual request uses the existing schema-v4 complete embedded source catalog
with no dependencies. Catalog admission does not pre-parse the entry. The
selected Wasm-AOT and spec-exec workers therefore run their original frontends
on the actual source, with the existing deadlines, process limits and durable
attempt journals. No eval, Function constructor, alternate parser or ambient
filesystem loader is introduced. A compiler accidentally accepting the source
encounters a finite generated program and produces a red observation.

The product's actual structured ParseDiagnostic supplies Parse versus EarlyError.
Unsupported parser features remain FrontendCapability failures. The optional
oracle carries a native entry-SyntaxError provenance bit from its actual
Script/Module parser into EngineError; it does not claim a separate grammar versus
static-semantics classification. User-thrown SyntaxErrors, module loading errors,
runtime failures, timeouts and worker failures cannot mint that provenance.

Only the expected product rejection phase, the oracle's actual entry syntax
rejection and two complete empty output transcripts satisfy a negative case.
The original differential report remains unchanged, normally `both_failed` and
red as an executable-program comparison. The separate campaign record states
the expected rejection and its result. Its immutable observation owner prevents
a caller from retaining a green flag while replacing the underlying report.
Foreign source fingerprints, goals and observation protocols are rejected.

A stable negative mismatch signature retains the expected product phase and
both actual phase/completion kinds. The reducer preserves those dimensions;
wording and each changed source fingerprint remain in the original reports.
Worker failure stops reduction and the enclosing campaign. Every attempted
source/report remains in the journal, including rejected reductions.

Run a campaign with the feature-enabled CLI:

```sh
lila differential campaign --output-dir fresh-negative --grammar negative-source-v1 \
  --seed 0 --cases 32 --steps 8 --depth 4 --max-replays 64 --oracle spec-exec
```

Final negative requests stay in `evidence/case-NNN.negative.json`, with their
typed expectation and unmodified report in `evidence/case-NNN.json`; they do
not enter the green executable corpus. `lila differential replay` on that
request reproduces the actual backend failures. The negative campaign applies
the expected-phase assertion explicitly. The existing serial CI campaign
tiers include this grammar.

Authored controls cover every construct/goal/strictness and reduced source,
wrong-phase/capability/runtime rejection, changed-source identity, minimization,
worker interruption and the oracle entry-versus-runtime SyntaxError boundary.
Source writing establishes no executed acceptance. General arbitrary-input
frontend fuzzing and sustained campaigns remain T25 work.
