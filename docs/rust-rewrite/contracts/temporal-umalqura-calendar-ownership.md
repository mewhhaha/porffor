# Umm al-Qura calendar ownership

`islamic-umalqura` is the thirteenth closed calendar identifier. It consumes a distinct UmmAlQura arithmetic case; `TemporalIslamicCalendar::{Civil,Tbla}` still owns only Type-II arithmetic. The actual `TemporalIslamicEraCalendar` selector shares AH/BH era membership with the resolver and accessor while keeping the arithmetic domains separate. AH resolves identically and BH resolves `1-eraYear`, including non-positive input era years; reporting chooses AH for a positive projected calendar year and BH otherwise. Bare `islamic` remains unsupported.

The [March 2026 era/month-code specification](https://tc39.es/proposal-intl-era-monthcode/) requires the exact AH1300..1600 table and civil arithmetic outside it. The literal flags and ISO year starts come from the [pinned ICU4X table](https://raw.githubusercontent.com/unicode-org/icu4x/31e2bfa8e39e069dcef6de3f6914c5d722e90d00/components/calendar/src/cal/hijri/ummalqura_data.rs), also present at `vendor/icu_calendar-2.0.6/src/cal/hijri/ummalqura_data.rs` (SHA256 `9e489ef9fd0fc7205213ca3c7ed1edb5523d8cf89d66d7e626a859b49dcbbe30`). The transformed native data retains the original Unicode permission notice and source attribution. No astronomical estimate or host calendar evaluator supplies product semantics.

Only the private checked `UmmAlQuraYearInfo` constructor can mint a packed year row. Its twelve low bits own the month flags together with the arithmetic-shifted signed Unix start. The consumed 301-row table validates the exact year census, each ISO literal, every 354/355-day total, contiguous starts, packing bounds and both civil joins. First and exclusive-end days come from these same validated rows. Balanced emitted year and epoch trees select actual validated records; projection membership is tested against the exact first start and exclusive end, and outside values call the existing Civil leaf. Inverse projection does not select a table row from the approximate tabular inverse.

The year and epoch trees now each have one shared pure Wasm helper. The year
lookup returns the packed row; the epoch lookup returns calendar year followed
by that row. The private caller consumes the pair together after the original
table-interval guard. Complete projection and calendar-to-ISO conversion are
shared too. Their [six-helper contract](temporal-east-asian-calendar-ownership.md#shared-pure-calendar-helpers--2026-10-06)
records exact result ordering, owned destinations and data-planning stubs.

The private emitted leaf has five actual parent consumers: month length, complete calendar-to-ISO conversion, ISO-to-calendar projection, final MonthDay reference, and absent-year MonthDay regulation-year selection. Table month lengths are 29 plus the actual bit, and month starts accumulate those real lengths. Projection fills the existing fields, ordinal, actual month length and 355-day flag; the sole parent year footer adds that flag to the exhaustive common base354. The same fixed count12 feeds add/difference, YearMonth rounding and private plain/zoned relative-date contexts, including virtual anchors before clamping. Existing ISO-backed carriers, allocations, constructor coordinates and annotated string coordinates remain the product representation. The parent’s conservative year envelope precedes integer conversion; full-date and YearMonth reference-month limits retain their completed owners; supplied MonthDay admission instead tests the whole native year before month information.

One uniform regulation year cannot preserve all valid MonthDay pairs. The private const-derived policy examines fully converted day30 candidates inside ISO1900-01-01..1972-12-31 and proves a latest candidate exists for every month. The actual absent-year branch selects that month-specific year before overflow regulation, so missing-year day31 constrains to30 for every M01..M12. Numeric `month` in a non-ISO MonthDay bag still requires a supplied year even when `monthCode` is also present. The shared month factory admits a supplied native year only when its actual start and next-year start intersect the full ISO carrier range. Those starts use this same table/civil conversion, including both validated joins. The requested month/day may lie outside that range or in an adjacent ISO year; after admission, regulation uses the supplied year’s actual table or civil month length. This follows the [current whole-year admission rule](https://tc39.es/proposal-intl-era-monthcode/#sec-nonisomonthdaytoisoreferencedate). Both final partial factories consume the same reference policy: day30 uses the latest long-month year; day1..29 starts in1392 and moves to1391 if the fully converted candidate exceeds the cutoff. Table1392 M12 is long but its day30 is in1973, so that pair selects1390.
