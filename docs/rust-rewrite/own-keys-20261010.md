# Ordinary and exotic own-key construction — 2026-10-10

Own-key construction previously compared each candidate against every earlier
key and repeatedly scanned the full list to select the next numeric index.
Both loops become quadratic as ordinary properties or indexed entries grow.

The physical key owners already enforce uniqueness and separate named keys
from exotic indexed keys. Candidate insertion now appends directly. One pass
gathers canonical numeric indices into a rooted ArrayIndexKeyConstruction;
the existing unsigned heap sort orders that prefix, then canonical decimal
Strings populate the result. Two final passes retain the insertion order of
other Strings and Symbols. Allocation follows the physical candidate count,
including for sparse arrays with large logical lengths.

The change preserves numeric ordering even when plain objects store numeric
names in reverse insertion order. Re-created numeric keys return to numeric
order; re-created non-index Strings and Symbols follow insertion order. The
new native control also covers indices above signed-i32 range, the maximum
array index, non-index numeric-looking names, an unpaired surrogate, accessors
that enumeration must not invoke, and empty/single-key lists.

Array, Arguments, String-box and TypedArray indexed keys have disjoint named
storage. Module namespaces retain the linker's UTF-16 ordering. Proxy trap
results still undergo their existing observable reads, duplicate detection and
target invariant validation; those paths do not use this candidate shortcut.
