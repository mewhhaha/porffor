# Realm intrinsic registry

This document defines the current Rust foundation for realm-owned ECMAScript
intrinsics. It is an architectural contract, not a claim that realm bootstrap
or cross-realm execution is complete.

## Identity model

An intrinsic identity is the pair `(RealmId, IntrinsicKind)`. The kind names a
specification intrinsic; the realm component prevents two realms from sharing
JavaScript object identity accidentally. Static registry data describes how a
fresh realm must build its graph, while `RealmIntrinsics` binds that data to one
realm.

Every intrinsic registry row carries five independent facts:

1. its stable `IntrinsicKind` and specification name;
2. its role during bootstrap;
3. its internal `[[Prototype]]`, if any;
4. callable metadata, if the intrinsic is a function;
5. its own constructor/prototype property relation, if any.

The internal `[[Prototype]]` and property relation are intentionally separate.
For example, `%Array%` inherits from `%Function.prototype%`, while its own
`"prototype"` property points to `%Array.prototype%`. Inferring one relation
from the other is incorrect.

## One declarative source

The registry macro is the only place that enumerates intrinsic rows. It emits:

- `IntrinsicKind` membership and order;
- `IntrinsicKind::ALL`;
- `INTRINSIC_DESCRIPTORS` and constant-time descriptor lookup;
- callable `"name"` and `"length"` property templates;
- constructor-to-prototype and prototype-to-constructor property templates.

Every row must spell all metadata fields, including explicit `none` values.
Adding an enum variant independently is impossible because the enum itself is
generated by the registry.

`IntrinsicLink` is a closed relation:

- `None` emits no link property;
- `ConstructorToPrototype` emits an own `"prototype"` property;
- `PrototypeToConstructor` emits an own `"constructor"` property.

Const evaluation derives the property count and property array from the same
descriptor rows. Compile-time validation requires exact row/property counts,
checks kind/order alignment, checks role-compatible link targets, and proves
that every link has the reciprocal relation. There is no fallback row and no
runtime repair pass.

## Bootstrap consumption

`RealmIntrinsics` resolves descriptors through the generated registry. Future
realm allocation must consume `INTRINSIC_DESCRIPTORS` and
`INTRINSIC_PROPERTY_DESCRIPTORS` directly when allocating objects and defining
properties; it must not rebuild family-specific tables in the backend.

Feature expansion should extend the registry schema only when a new piece of
bootstrap data is genuinely shared. Feature-specific methods and algorithms do
not belong in this table.

## Defining-realm attachment

The Wasm emitter represents a proven realm-record local as
`RealmRecordLocal`. Its constructor is private to realm allocation, so the
created-realm function materializer cannot receive an arbitrary payload, tag
or scratch local. That materializer allocates the function and writes its
defining-realm reference before returning the destination local. Created-realm
bootstrap must not recreate the former two-statement allocate-then-repair
pattern.

Function environment/self-backing is deliberately not folded into this type.
It controls how a builtin invocation finds additional realm snapshots and is
not identical to the specification's defining-realm reference.

The emitted `GetFunctionRealm` traversal has three closed outcomes: resolved,
revoked and invalid. Its raw realm/outcome locals are private and must be
consumed by one routing operation before a resolved realm local becomes
available. That operation always traps `invalid`; its closed revoked policy
either emits the constructor/default-prototype `TypeError` and exits the
current control-flow region, or selects the current realm where Promise job
creation requires that fallback. A caller therefore cannot read the realm and
forget one of the two nonresolved cases. This does not claim that every
intrinsic slot is complete: the existing prototype loader still has explicit
global/local fallbacks for partially bootstrapped families, which must
disappear as the registry becomes the full allocation source.

## Remaining work

The registry currently covers the checked-in 23-intrinsic foundation, not the
complete ECMAScript intrinsic set. T06 remains open for independently allocated
intrinsic objects, full global/environment bootstrap, complete defining-realm
coverage, realm-correct error creation, teardown, host hooks, and the
cross-realm acceptance matrix. T03 shortcut materializations must be removed
as those general semantics land.
